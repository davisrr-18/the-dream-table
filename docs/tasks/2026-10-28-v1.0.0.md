## Architectural conclusions

- A direct Forge/NeoForge port would duplicate or entangle loader-specific registration, lifecycle, networking, client rendering, and configuration code.
- The first implementation step should be a minimal proof of concept, not a broad refactor or a full port.
- The proof of concept must establish whether a common core plus thin loader adapters is viable with the current Minecraft 1.21.1 APIs and build tooling.
- Existing save keys, payload semantics, screen slot coordinates, and server-authority rules remain compatibility invariants.

### Decision

The multiplatform approach is feasible in principle, but Marco 2 cannot meet its exit criterion yet: no reproducible three-loader baseline has been validated. The current Fabric module must not be split based on inferred plugin or mapping combinations. In particular, supporting Fabric, Forge, and NeoForge must be demonstrated in an isolated, reproducible prototype before common code is introduced.

### Approved POC boundary for a future attempt

1. A separate prototype with `common`, `fabric`, `forge`, and `neoforge` modules.
2. A deliberately tiny vertical slice: content registration, client/server initializers, one authenticated request, one persisted counter/state, and one rendered block/item.
3. Independent build and smoke checks for each loader, one at a time.
4. No imports, save keys, packet semantics, or existing product classes move until all three builds pass.
